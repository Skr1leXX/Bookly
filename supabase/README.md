# Supabase для Bookly

- `migrations/` — схема (`…_schema.sql`) и RLS (`…_rls.sql`). Применяются по порядку.
- `seed.sql` — демо-данные (две организации, 6 пользователей, ~240 записей; даты относительно сегодняшнего дня).
- `tests/` — проверки на встроенном Postgres (PGlite), Docker не нужен: `npm run test:db`.

## Локально
```bash
npx supabase start        # поднимает Postgres + Auth; выведет URL и anon key для .env.local
npx supabase db reset     # миграции + seed.sql
```
Без Docker: в облачном проекте выполните файлы из `migrations/` по порядку в SQL Editor, затем `seed.sql`
(только для демо-проекта: сид пересоздаёт демо-пользователей).

## Права
| | owner | admin | staff |
|---|---|---|---|
| Чтение данных своей организации | ✓ | ✓ | ✓ |
| Клиенты: создание/правка | ✓ | ✓ | ✓ |
| Клиенты, записи: удаление | ✓ | ✓ | — |
| Записи: создание | ✓ | ✓ | ✓ |
| Записи: правка | любые | любые | только свои (staff.user_id) |
| Услуги, специалисты, график | ✓ | ✓ | только чтение |
| Участники; роль owner | ✓ / ✓ | ✓ / — | — |
| Настройки организации; удаление организации | ✓ ✓ | ✓ — | — |
| Уведомления | только свои | только свои | только свои |

Ключ `service_role` приложению не нужен и нигде не используется: все запросы идут от имени пользователя (anon key + JWT из cookie), доступ ограничивает RLS.

## Проверка без Docker
- `npm run test:db` — RLS, роли, правила записи, RPC, загрузчик данных и логика приложения (PGlite).
- `npm run emulator` — локальная замена Supabase (GoTrue + часть PostgREST) на PGlite с теми же миграциями и seed.
  Запустите приложение с `NEXT_PUBLIC_SUPABASE_URL=http://127.0.0.1:54321` и любым `NEXT_PUBLIC_SUPABASE_ANON_KEY`.
  Это не настоящий PostgREST: только то, что использует приложение. Данные живут в памяти до перезапуска.

## Бизнес-правила в БД
- Запись нельзя пересечь по времени с другой записью того же специалиста (отменённая освобождает слот).
- Активная запись (ожидает/подтверждена): специалист и услуга включены, специалист оказывает услугу и работает в это время.
- `save_staff` и `save_company` — RPC: специалист, его услуги и расписание (организация и часы работы) сохраняются одной транзакцией.

## Публичная онлайн-запись
Страница `/book/<slug>` (slug организации; ссылка есть в «Настройках»), аккаунт клиенту не нужен.
- Анонимный посетитель не имеет доступа к таблицам. Он вызывает четыре функции `public_org`, `public_slots`, `public_book`, `public_appointment`
  (SECURITY DEFINER): они отдают только публичные данные и сами создают запись.
- Свободное время считает одна SQL-функция `_slots` (рабочие часы, перерыв, длительность, существующие записи, не раньше чем через час,
  не дальше 60 дней). Те же правила повторно проверяются в `public_book` под advisory-lock непосредственно перед вставкой;
  от гонок защищает и ограничение на пересечение записей.
- Запись создаётся со статусом «Ожидает подтверждения» и пометкой `source = online`; владельцам и администраторам приходит уведомление.
- Защита от спама: honeypot-поле и минимальное время заполнения (на сервере Next), в БД — лимиты по IP-хэшу (5 попыток / 10 мин),
  по телефону (5 / 10 мин), по организации (30 / 10 мин, 200 онлайн-записей в сутки), не более 3 активных будущих записей на телефон.
  Лимит по IP опирается на значение, которое присылает приложение; лимиты по телефону и организации не зависят от него.
